# Contributing to KamiTrace

Welcome! **KamiTrace is in its foundational iteration.** Our primary objective is to standardize the **96-Point Multi-Layered Civic AI Audit framework** before coding and running active audits. 

Alternatively, this initiative may remain an educational project designed to popularize the **"6-Pack of Care" framework** and spark broad civic discussion regarding the evaluation of various institutions developing AI technologies. We need your help to stress-test, refine, and code the parameters of this evaluation engine.

> 🚨 **Alpha Notice:** We are **NOT** accepting real-world lab audit submissions, whistleblower telemetry data, or active brand evaluation logs at this stage. All contributions must be strictly limited to methodology modifications, blueprint updates, and code proposals.

---

## 🤖 Open-Source AI Guidelines

This is an educational project. Contributions, structural fixes, methodology expansions, and documentation edits are highly welcome. 

Please note that the baseline documentation has been structurally refined using Google's Gemini model. In the spirit of open-source transparency, we encourage all future contributors to disclose any generative AI workflows or models used to assist in their pull requests.

## Track A: Methodology & Framework Ethicists
Focus on refining the conceptual, structural, and linguistic foundation of the audit criteria.

### 1. Contribution Targets
*   **Structural Review**: Audit and provide direct feedback on the viability of the 3 invariant analytical vectors (Input Authority, Processing Resolution, and Fallback Humility).
*   **Footprint Assessment**: Evaluate the cross-referencing capabilities of the 4 forensic media footprints (Written, Spoken, User Feedback, and Telemetry).
*   **Verification Verification**: Review, stress-test, and provide concrete feedback on the specific verification cases outlined under each core pack in the `/checklists` directory.

### 2. How to Submit Changes
*   **General Public:** Post your proposals, metric text adjustments, or validation rubric changes directly in the **GitHub Discussions** tab. Use markdown tables to show comparisons between existing rules and your proposed revisions.
*   **Approved Contributors Only:** You may open a formal Issue to track structural adjustments or grading threshold updates.

## Track B: Dashboard Architects & Data Engineers
Focus on reviewing the proposed calculation engine and designing the first physical software iteration.

### 1. Contribution Targets
*   **Architecture Gap Analysis**: Review the current dashboard engine proposal and identify architectural omissions, boundary flaws, or engineering limitations.
*   **First-Iteration Blueprint**: Outline and draft a reasonable, minimal viable product (MVP) layout for the initial dashboard deployment.
*   **Data Layout Design**: Developing the columns, constraints, and data validation rules for the foundational scorecard file (`/checklists/scorecard.csv`).

### 2. How to Submit Changes
*   **General Public:** Share your design documents, flowchart definitions, or architecture gap analyses as text or code blocks inside the **GitHub Discussions** tab for open community vetting.
*   **Approved Contributors Only:** You may submit markdown definitions or schema updates directly to the `/dashboard` directory. Verify that your proposed algorithmic changes do not disrupt the mathematical balancing required to calculate the final Alignment Deficit Score (ADS).

## 3. Repository Guidelines & Intake Status

To protect the integrity of the framework and maintain a clear legal architecture before we transition to full open-source distribution, we operate under three strict constraints:

*   **View-Only/Read-Only Phase**: Our root license dictates that outside modifications or derivative distributions are legally restricted. You are invited to review, audit, and evaluate the engine blueprints locally, but the code remains strictly "look-but-don't-touch" for the general public right now.
*   **Discussions Section is the Way to Go**: Public Pull Requests and Issues are technically locked to designated project collaborators. The **GitHub Discussions tab is our primary avenue for community engagement**. Please pitch your ideas, engineering gap analyses, or framework modifications there so the community can vet them.
*   **Copyright Assignment & Open-Source Pathway**: If you are added as an approved contributor to submit an internal Pull Request, you explicitly agree that your contributions become the sole copyright property of the project owner. This ensures a clean, undisputed codebase, giving us a seamless path to transition the framework to a fully open-source distribution model (such as MIT) once community traction is validated.
